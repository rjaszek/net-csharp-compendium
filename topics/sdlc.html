SDLC — Software Development Life Cycle

Co to jest

SDLC (Software Development Life Cycle, cykl życia oprogramowania) to ustrukturyzowany proces opisujący wszystkie fazy powstawania i utrzymania oprogramowania — od zebrania wymagań, przez projekt i implementację, aż po wdrożenie i dalsze wsparcie. To nie jest konkretna metodologia (jak Scrum czy Waterfall) — to ogólny model fazowy, który każda metodologia w jakiś sposób realizuje (sekwencyjnie, iteracyjnie, ciągle).

6 faz SDLC

1. Planning / Requirements Analysis (planowanie i analiza wymagań)

Zbieranie wymagań biznesowych i technicznych, określenie zakresu, szacowanie kosztu i czasu, identyfikacja ryzyk. Efekt: dokument wymagań (funkcjonalnych i niefunkcjonalnych), backlog produktu.

2. Design (projektowanie)

Projekt architektury systemu: podział na moduły/serwisy, wybór wzorców (np. SOLID, MVVM, CQRS — patrz odpowiednie tematy na tej stronie), projekt bazy danych, API, UI/UX. Efekt: dokumentacja architektoniczna, diagramy, kontrakty API.

3. Implementation / Coding (implementacja)

Pisanie kodu zgodnie z projektem i standardami zespołu (code style, code review). Tu w praktyce żyje większość tematów technicznych z tej strony — wzorce projektowe, DI, EF Core, Web API.

4. Testing (testowanie)

Weryfikacja, że oprogramowanie działa zgodnie z wymaganiami i nie zawiera regresji: testy jednostkowe (xUnit, Moq), testy integracyjne, testy manualne/UAT (User Acceptance Testing). Efekt: raporty z testów, lista wykrytych błędów.

5. Deployment (wdrożenie)

Udostępnienie oprogramowania użytkownikom: budowanie, migracja bazy danych (EF Core migrations), konteneryzacja i orkiestracja (Docker, Kubernetes), wdrożenie na środowisko produkcyjne (często przez pipeline CI/CD).

6. Maintenance (utrzymanie)

Monitorowanie działania systemu na produkcji, naprawa błędów (bugfixing), wsparcie użytkowników, wprowadzanie drobnych usprawnień. Ta faza trwa najdłużej w całym cyklu życia projektu — często dłużej niż wszystkie poprzednie razem wzięte.

Planning → Design → Implementation → Testing → Deployment → Maintenance
                                                                    │
                                                                    ▼
                                                        (wraca do Planning dla
                                                         kolejnych wersji/funkcji)

Modele / metodologie realizujące SDLC

Powyższe fazy są wspólne dla każdego podejścia — różnica jest w tym, jak te fazy są rozłożone w czasie.

Waterfall (model kaskadowy)

Fazy wykonywane sekwencyjnie, jedna po drugiej, bez powrotu do poprzedniej (w teorii). Cały projekt jest najpierw w pełni zaplanowany i zaprojektowany, zanim zacznie się kodowanie.

Planning → Design → Implementation → Testing → Deployment → Maintenance
   (każda faza kończy się w 100% przed startem następnej)

Zalety: przewidywalność, jasna dokumentacja, dobrze działa dla projektów z niezmiennym, dobrze znanym z góry zakresem (np. systemy regulowane prawnie).

Wady: błąd w wymaganiach wykryty na etapie testowania jest bardzo kosztowny do naprawienia (trzeba wrócić na początek); brak elastyczności na zmiany; klient widzi działający produkt bardzo późno.

Agile / Scrum

Praca podzielona na krótkie, iteracyjne cykle (sprinty), zwykle 1-4 tygodnie. W każdym sprincie powstaje mały, ale kompletny i działający przyrost produktu — czyli w każdym sprincie w miniaturze przechodzimy przez planning → design → implementation → testing → (często) deployment.

Sprint 1: Plan → Design → Code → Test → Review  ─┐
Sprint 2: Plan → Design → Code → Test → Review  ─┼─► przyrosty produktu
Sprint 3: Plan → Design → Code → Test → Review  ─┘    (ciągła informacja zwrotna)

Zalety: szybka informacja zwrotna od klienta, łatwa adaptacja do zmieniających się wymagań, działający produkt widoczny od wczesnego etapu.

Wady: wymaga dużego zaangażowania klienta/product ownera, trudniej przewidzieć dokładny koniec i koszt całego projektu z góry.

DevOps / CI-CD (continuous integration / continuous delivery)

Rozszerza Agile o automatyzację i zatarcie granicy między Development i Operations — kod jest budowany, testowany i wdrażany ciągle, często wiele razy dziennie, przez automatyczny pipeline.

Commit → Build → Automated Tests → (EF Core migrations) → 
  → Containerize (Docker) → Deploy (Kubernetes) → Monitor
  (cały łańcuch odpalany automatycznie przy każdym commicie/merge'u)

Zalety: bardzo szybkie wykrywanie błędów (fail fast), małe, częste, mniej ryzykowne wdrożenia, silne powiązanie Testing-Deployment-Maintenance w jeden ciągły proces.

Wady: duży koszt wstępny (infrastruktura CI/CD, automatyzacja testów), wymaga kultury organizacyjnej gotowej na częste wdrożenia.

V-Model (model weryfikacji i walidacji)

Rozszerzenie Waterfall, w którym każdej fazie projektowej odpowiada symetrycznie faza testowa — planowana równolegle, zanim jeszcze napisano kod.

Requirements Analysis  ──────────────────────  Acceptance Testing
      │                                                │
  System Design       ──────────────────────    System Testing
      │                                                │
  Architecture Design ──────────────────────  Integration Testing
      │                                                │
  Module Design       ──────────────────────      Unit Testing
      │                                                │
      └──────────────────► Coding ────────────────────┘

Zalety: testy są zaplanowane od samego początku (nie są "doklejane" na końcu), wysoka wykrywalność błędów na wczesnym etapie.

Wady: tak samo sztywny jak Waterfall — słabo radzi sobie ze zmieniającymi się wymaganiami.

Porównanie

Model Elastyczność Kiedy wykrywane błędy Typowe zastosowanie
Waterfall niska późno (faza Testing) projekty z ustalonym z góry, niezmiennym zakresem (np. systemy regulowane)
Agile/Scrum wysoka na bieżąco, co sprint produkty z ewoluującymi wymaganiami, startupy, większość dzisiejszego software house
DevOps/CI-CD bardzo wysoka natychmiast po commicie zespoły z dojrzałą automatyzacją, częste wdrożenia (SaaS, mikroserwisy)
V-Model niska wcześnie zaplanowane, ale sztywno projekty safety-critical (medycyna, lotnictwo, finanse)

Dlaczego to pytanie pada na rozmowach na stanowisko SE III

Na poziomie Senior/SE III rekruterzy oczekują nie tylko umiejętności kodowania, ale świadomości procesu — zrozumienia, że kod który piszesz jest jednym z ogniw większego cyklu: że decyzje projektowe (Design) wpływają na koszt testowania (Testing) i wdrożenia (Deployment), że błąd złapany w Code Review jest dziesiątki razy tańszy niż złapany na produkcji, i że umiejętność doboru odpowiedniego modelu (Waterfall vs Agile vs DevOps) do kontekstu projektu jest realną kompetencją inżynierską, nie tylko "papierologią".
