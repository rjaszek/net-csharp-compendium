.NET / C# / WPF

WPF - co warto odświeżyć przed rozmową SE III

Poza MVVM/DI, na rozmowach o WPF (zwłaszcza na poziomie III) lubią sprawdzić zrozumienie mechanizmów "pod spodem", nie tylko umiejętność klikania w XAML. Oto co bym przypomniał, pogrupowane tematycznie.

1. Dependency Properties - fundament WPF

To prawdopodobnie najczęściej pytany temat poza samym MVVM - różnica między zwykłą właściwością C# a Dependency Property.

public class RatingControl : Control
{
    public static readonly DependencyProperty ValueProperty =
        DependencyProperty.Register(
            nameof(Value),
            typeof(int),
            typeof(RatingControl),
            new FrameworkPropertyMetadata(
                defaultValue: 0,
                FrameworkPropertyMetadataOptions.BindsTwoWayByDefault,
                OnValueChanged));

    public int Value
    {
        get => (int)GetValue(ValueProperty);
        set => SetValue(ValueProperty, value);
    }

    private static void OnValueChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        // reakcja na zmianę wartości
    }
}

Dlaczego DP istnieje, a nie zwykłe { get; set; }: - Wbudowane wsparcie dla data bindingu (bez ręcznego INotifyPropertyChanged) - Property value inheritance - dziedziczenie wartości po drzewie wizualnym (np. FontSize, DataContext) - Wsparcie dla stylów, animacji, triggerów - to wszystko działa tylko na DP - Automatyczna redukcja pamięci - DP nie zajmuje pamięci per-instancja, jeśli ma wartość domyślną (przechowywane w słowniku statycznym)

Attached Property - podobne, ale "przyczepiane" do dowolnego elementu, nie tylko właściciela:

// Grid.Row, Grid.Column to klasyczne attached properties
<Button Grid.Row="0" Grid.Column="1" />

2. Routed Events - bubbling vs tunneling

Częste pytanie: "Czym różni się PreviewMouseDown od MouseDown?"

Tunneling (Preview...): od korzenia drzewa W DÓŁ do elementu źródłowego
Bubbling (bez Preview): od elementu źródłowego W GÓRĘ do korzenia

<StackPanel MouseDown="Parent_MouseDown">
    <Button Content="Kliknij" MouseDown="Button_MouseDown" />
</StackPanel>

Kliknięcie w przycisk: najpierw leci PreviewMouseDown od okna w dół do przycisku (tunneling), potem MouseDown od przycisku w górę do okna (bubbling). Można zatrzymać propagację przez e.Handled = true.

3. Data binding - szczegóły, które łatwo zapomnieć

<!-- Mode: OneWay, TwoWay, OneTime, OneWayToSource, Default -->
<TextBox Text="{Binding UserName, Mode=TwoWay, UpdateSourceTrigger=PropertyChanged}" />

<!-- RelativeSource - binding do właściwości przodka w drzewie -->
<TextBlock Text="{Binding DataContext.Title, RelativeSource={RelativeSource AncestorType=Window}}" />

<!-- ElementName - binding do innego elementu na tej samej stronie -->
<Slider x:Name="VolumeSlider" Maximum="100" />
<TextBlock Text="{Binding Value, ElementName=VolumeSlider}" />

IValueConverter - konwersja danych między Model a View:

public class BoolToVisibilityConverter : IValueConverter
{
    public object Convert(object value, Type targetType, object parameter, CultureInfo culture)
        => (bool)value ? Visibility.Visible : Visibility.Collapsed;

    public object ConvertBack(object value, Type targetType, object parameter, CultureInfo culture)
        => throw new NotImplementedException();
}

ObservableCollection - dlaczego zwykła List<T> nie wystarczy w bindingu do ItemsControl:

// Źle - zmiana zawartości NIE powiadomi UI
public List<Order> Orders { get; set; } = new();

// Dobrze - implementuje INotifyCollectionChanged
public ObservableCollection<Order> Orders { get; set; } = new();

4. Visual Tree vs Logical Tree

Częste pytanie koncepcyjne: - Logical Tree - struktura elementów zdefiniowana w XAML (to co Ty piszesz) - Visual Tree - pełna struktura renderowanych elementów, włącznie z tymi wygenerowanymi przez template'y (np. wewnętrzne części Button - Border, ContentPresenter)

// Przeszukiwanie visual tree - typowe zadanie na "znajdź rodzica/dziecko określonego typu"
public static T FindVisualParent<T>(DependencyObject child) where T : DependencyObject
{
    var parent = VisualTreeHelper.GetParent(child);
    if (parent == null) return null;
    return parent as T ?? FindVisualParent<T>(parent);
}

5. Threading - Dispatcher i UI thread

To jest bardzo częsty temat na rozmowach - WPF ma model single-threaded UI (tzw. STA - Single Threaded Apartment).

// Błąd - wyjątek "The calling thread cannot access this object"
private async Task LoadDataAsync()
{
    var data = await Task.Run(() => _repository.GetOrders()); // background thread
    OrdersList.ItemsSource = data; // ❌ próba dostępu do UI z innego wątku
}

// Dobrze - Dispatcher.Invoke wraca na UI thread
private async Task LoadDataAsync()
{
    var data = await Task.Run(() => _repository.GetOrders());
    Application.Current.Dispatcher.Invoke(() =>
    {
        OrdersList.ItemsSource = data;
    });
}

// Jeszcze lepiej - async/await z SynchronizationContext WPF
// automatycznie wraca na UI thread po await, jeśli nie użyjesz ConfigureAwait(false)
private async Task LoadDataAsync()
{
    var data = await _repository.GetOrdersAsync(); // wraca na UI thread automatycznie
    OrdersList.ItemsSource = data; // ✅ OK
}

Warto umieć wytłumaczyć dlaczego - await domyślnie przechwytuje SynchronizationContext i wraca na ten sam wątek (UI thread), chyba że użyjesz ConfigureAwait(false) (co w kodzie ViewModelu zwykle nie chcesz robić, bo potem musisz wrócić na UI thread ręcznie).

6. Styles, Templates, Triggers

<Style TargetType="Button" x:Key="PrimaryButtonStyle">
    <Setter Property="Background" Value="DodgerBlue" />
    <Style.Triggers>
        <!-- DataTrigger - reakcja na wartość z bindingu -->
        <DataTrigger Binding="{Binding IsEnabled, RelativeSource={RelativeSource Self}}" Value="False">
            <Setter Property="Opacity" Value="0.5" />
        </DataTrigger>
        <!-- Trigger - reakcja na właściwość samego elementu -->
        <Trigger Property="IsMouseOver" Value="True">
            <Setter Property="Background" Value="RoyalBlue" />
        </Trigger>
    </Style.Triggers>
</Style>

ControlTemplate vs DataTemplate - różnica, którą warto umieć wyjaśnić: - ControlTemplate - definiuje jak wygląda kontrolka (np. jak wygląda Button od środka - Border, ContentPresenter) - DataTemplate - definiuje jak wyświetlić dane (np. jak ma wyglądać pojedynczy element w ListBox bindowany do obiektu Order)

7. Wydajność - typowe pytanie "co byś zoptymalizował"

  • UI Virtualization w ItemsControl/ListBox - żeby nie renderować tysięcy elementów naraz (VirtualizingStackPanel.IsVirtualizing="True", domyślnie włączone w nowszych wersjach)
  • Freezable objects (np. Brush, Geometry) - wywołanie .Freeze() poprawia wydajność, bo WPF nie musi nasłuchiwać zmian
  • Unikanie zbyt głębokiego zagnieżdżenia Binding z Converter wykonującym ciężkie obliczenia (binding może się odpalać bardzo często)

Biorąc pod uwagę doświadczenie w C#, prawdopodobnie większość z tego "siedzi" gdzieś w pamięci mięśniowej - najbardziej prawdopodobne pytania na SE III to te bardziej konceptualne (DP vs zwykła property, dlaczego Dispatcher, bubbling vs tunneling, Visual vs Logical Tree), bo sprawdzają zrozumienie dlaczego WPF działa tak jak działa, a nie samą składnię.
