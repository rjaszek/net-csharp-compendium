PWA (Progressive Web App) w kontekście Blazor

Co to jest PWA - ogólnie

PWA to zestaw technik webowych sprawiających, że strona internetowa zachowuje się jak natywna aplikacja: można ją "zainstalować" (ikonka na pulpicie/ekranie głównym), może działać (częściowo) offline, może wysyłać powiadomienia push, otwiera się w osobnym oknie bez paska adresu przeglądarki.

Kluczowe elementy PWA

1. Web App Manifest (manifest.json) - metadane aplikacji:

{
  "name": "Order Management System",
  "short_name": "OrderMgmt",
  "start_url": "/",
  "display": "standalone",
  "icons": [
    { "src": "icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}

To pozwala przeglądarce pokazać opcję "Zainstaluj aplikację" i sprawić, że otwiera się jak natywne okno, bez UI przeglądarki.

2. Service Worker - skrypt JS działający w tle, niezależnie od otwartej karty, przechwytujący requesty sieciowe:

// service-worker.js (uproszczony przykład)
self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(cached => cached || fetch(event.request))
  );
});

Service Worker cache'uje pliki statyczne (HTML, CSS, JS, a w przypadku Blazor WASM - też skompilowane assembly .NET), dzięki czemu aplikacja może się załadować i częściowo działać bez połączenia internetowego.

PWA + Blazor WebAssembly - naturalne połączenie

To jest ważny punkt koncepcyjny: PWA ma sens praktyczny głównie z Blazor WASM, nie z Blazor Server.

Dlaczego: - Blazor WASM uruchamia cały kod aplikacji lokalnie w przeglądarce (skompilowany do WebAssembly) - jeśli te pliki są scache'owane przez Service Worker, aplikacja faktycznie może działać offline (UI się renderuje, lokalna logika działa) - Blazor Server wymaga stałego połączenia WebSocket z serwerem (cały "circuit" i stan żyje na serwerze) - offline w ogóle nie ma sensu, bo bez połączenia nic nie może się wykonać (nawet kliknięcie przycisku wymaga round-tripu do serwera)

dotnet new blazorwasm --pwa -o MyApp

Ten szablon generuje projekt Blazor WASM z gotowym manifest.json i service-worker.js.

Ograniczenia PWA z Blazor WASM w praktyce

  • Dane wymagające backendu (baza danych, autoryzacja serwerowa) i tak nie zadziałają offline - PWA daje offline dla UI i logiki lokalnej, nie dla operacji wymagających serwera
  • Synchronizacja danych po powrocie online wymaga własnej logiki (np. kolejkowanie zmian lokalnie, wysłanie ich gdy połączenie wróci) - Blazor tego nie robi automatycznie
  • Rozmiar pobrania jest większy (cały runtime .NET do WASM), więc pierwsze ładowanie offline-first bywa wolniejsze niż klasyczny SPA w czystym JS

Render Modes w Blazor (.NET 8+) - "Blazor United"

To jest jeden z największych architektonicznych zwrotów w Blazor - .NET 8 połączył Blazor Server i WASM w jeden model, z możliwością wyboru trybu renderowania per komponent.

Cztery tryby renderowania

1. Static Server Rendering (SSR) - domyślny, bez interaktywności

@page "/orders"
@rendermode InteractiveServer  <!-- lub brak = static -->

Renderowane raz na serwerze do statycznego HTML, wysłane do przeglądarki. Brak interaktywności - żadnych @onclick, żadnego stanu C# działającego po stronie klienta. To jak klasyczny, tradycyjny server-rendered HTML (podobne do starego Razor Pages/MVC).

Kiedy: strony treściowe (blog, dokumentacja, landing page) - szybkie, bez narzutu SignalR/WASM.

2. Interactive Server

@page "/orders"
@rendermode InteractiveServer

To jest dokładnie ten model Blazor Server, który opisałem wyżej - SignalR, circuit na serwerze, cała logika C# wykonuje się server-side.

Kiedy: aplikacje wymagające szybkiego czasu do pierwszej interakcji (nie czekasz na pobranie WASM), gdzie stały ruch sieciowy nie jest problemem (np. wewnętrzne narzędzia firmowe, intranet).

3. Interactive WebAssembly

@page "/orders"
@rendermode InteractiveWebAssembly

To klasyczny Blazor WASM opisany wcześniej - kod pobrany i wykonywany w przeglądarce.

Kiedy: potrzebujesz PWA/offline, chcesz odciążyć serwer (logika działa u klienta), aplikacja publiczna z wieloma jednoczesnymi userami (nie martwisz się o circuits/pamięć serwera).

4. Interactive Auto - "najlepsze z obu światów"

@page "/orders"
@rendermode InteractiveAuto

Najciekawszy, nowy tryb: przy pierwszym ładowaniu strony używa Blazor Server (szybki start, bez czekania na pobranie WASM), a w tle po cichu pobiera pliki WebAssembly. Przy kolejnych odwiedzinach tej samej aplikacji (WASM już scache'owany w przeglądarce) automatycznie przełącza się na WebAssembly - szybsze interakcje, mniej obciążenia serwera.

To rozwiązuje klasyczny dylemat "Server (szybki start, ale zależny od sieci) vs WASM (wolny start, ale szybki potem)" - użytkownik dostaje szybki start za pierwszym razem i szybkie działanie za każdym kolejnym.

Per-komponent, nie tylko per-aplikacja

Kluczowa elastyczność .NET 8 - różne komponenty w tej samej aplikacji mogą mieć różne render mode:

@* Strona główna - statyczna, szybka, SEO-friendly *@
@page "/"
<HomePage />

@* Panel administracyjny - interaktywny, server-side *@
@page "/admin"
@rendermode InteractiveServer
<AdminDashboard />

@* Kalkulator w przeglądarce - offline-capable *@
@page "/calculator"
@rendermode InteractiveWebAssembly
<Calculator />

To pozwala świadomie dobrać technologię do konkretnej części aplikacji - strona marketingowa nie potrzebuje SignalR ani WASM, panel admina może korzystać z Blazor Server (mało userów, dane wrażliwe lepiej zostają na serwerze), a publiczny kalkulator może być WASM (offline, brak obciążenia serwera).

Podsumowanie - dobra odpowiedź na rozmowę o Render Modes

"Render Modes w .NET 8 rozwiązują odwieczny dylemat Blazor Server vs WASM, pozwalając wybrać model per-komponent zamiast dla całej aplikacji. Static SSR do treści bez interaktywności, Interactive Server gdy zależy mi na szybkim starcie i nie przeszkadza stałe połączenie WebSocket, Interactive WebAssembly gdy potrzebuję PWA/offline albo chcę odciążyć serwer, a Interactive Auto to kompromis - szybki start przez Server przy pierwszej wizycie, płynne przejście na WASM przy kolejnych, gdy pliki są już scache'owane."
